# Triage

Move issues on project tracker through small state machine of triage roles.

If repo treat external PRs as request surface (see issue-tracker config), triage covers them too: **a PR is an issue with attached code** — same roles, same states, same machine, few deltas marked "for a PR" below. Resolve bare `#42` to issue or PR per tracker config.

Every comment or issue posted to tracker during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — how to write durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — how `.out-of-scope/` knowledge base works

## Roles

Two **category** roles:

- `bug` — something broken
- `enhancement` — new feature or improvement

Five **state** roles:

- `needs-triage` — maintainer needs evaluate
- `needs-info` — waiting reporter for more info
- `ready-for-agent` — fully specified, ready for AFK agent
- `ready-for-human` — needs human implementation
- `wontfix` — never actioned

For a PR, same states read against attached code: `ready-for-agent` means brief attached, agent takes next step on diff; `ready-for-human` means ready for human merge.

Every triaged issue carries exactly one category role + one state role. If state roles conflict, flag + ask maintainer before anything else.

These are canonical role names — actual label strings in tracker may differ. Mapping should have been provided to you - run `/setup-matt-pocock-skills` if not.

State transitions: unlabeled issue normally goes `needs-triage` first; from there moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once reporter replies. Maintainer can override anytime — flag transitions that look unusual, ask before proceeding.

## Invocation

Maintainer invokes `/triage`, describes want in natural language. Interpret request, act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query tracker, present three buckets, oldest first:

1. **Unlabeled** — never triaged.
2. **`needs-triage`** — evaluation in progress.
3. **`needs-info` with reporter activity since last triage notes** — needs re-evaluation.

When PRs in scope, include external PRs in buckets, tag each line `[PR]` or `[issue]`. Discovery surfaces only *external* PRs (tracker config defines who counts as external) — collaborator's in-flight PR not triage work. This filter discovery-only; explicitly named PR always triaged regardless of author.

Show counts + one-line summary per item. Let maintainer pick.

## Triage a specific issue or PR

1. **Gather context.** Read full issue or PR (body, comments, labels, author, dates; for PR, diff too). Parse prior triage notes so not re-ask resolved questions. Explore codebase using project's domain glossary, respect ADRs in area. Run two checks against codebase: (a) **redundancy** — search for existing implementation of requested behavior by domain concept (not just request's wording), report where looked. If found, already-implemented `wontfix` (step 5). (b) **prior rejection** — read `.out-of-scope/*.md`, surface any resembling request.

2. **Recommend.** Tell maintainer category + state recommendation with reasoning, plus brief codebase summary relevant to request — including whether already implemented. Wait for direction.

3. **Verify the claim.** Before grilling, check claim holds up. For bug, reproduce from reporter's steps. For PR, confirm diff does what claims — check it out, run relevant tests or commands. Report what happened: confirmed (with code path), failed, or insufficient detail (strong `needs-info` signal). Confirmed verification makes stronger agent brief.

4. **Grill (if needed).** If request needs fleshing out, run `/grilling` + `/domain-modeling` skills together — grill into shape one question at a time, sharpen domain terms, update `CONTEXT.md`/ADRs inline as decisions land.

5. **Apply the outcome:**
   - `ready-for-agent` — post agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human` — same structure as agent brief, note why can't delegate (judgment calls, external access, design decisions, manual testing).
   - `needs-info` — post triage notes (template below).
   - `wontfix` — close, comment depends on *why*:
     - **Already implemented** — the change already exists in the codebase. Point to where it lives; do **not** write to `.out-of-scope/` (that KB is for *rejected* requests, not built ones).
     - **Rejected (bug)** — polite explanation, then close.
     - **Rejected (enhancement)** — write to `.out-of-scope/`, link to it from a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage` — apply role. Optional comment if partial progress.

## Quick state override

If maintainer says "move #42 to ready-for-agent", trust them, apply role directly. Confirm about to do (role changes, comment, close), then act. Skip grilling. If moving to `ready-for-agent` without grilling session, ask whether want to write agent brief.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so work not lost. Questions must be specific + actionable, not "please provide more info".

## Resuming a previous session

If prior triage notes exist on issue or PR, read them, check whether reporter answered outstanding questions, present updated picture before continuing. Don't re-ask resolved questions.
